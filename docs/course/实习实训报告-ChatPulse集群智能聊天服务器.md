# 1. 引言

## 1.1 编写目的

本文档是《软件架构与应用开发实践》课程的大作业报告，针对课题"集群智能聊天服务器（ChatPulse）"完整阐述系统的架构设计过程与原型实现情况。文档面向课程指导教师与答辩评审，说明系统选型理由、五视图架构设计、数据库设计、非功能性需求解决方案以及原型系统的实现与验证，证明作者掌握了大型软件系统从需求分析到架构设计再到原型实现的工程化方法。

## 1.2 业务背景

即时通信（IM）是互联网最基础、用户量最大的应用形态之一。从企业内部的协作办公到面向公众的社交产品，IM 系统的核心链路（注册登录、好友关系、消息收发、离线补偿）是一条几乎不变的主干业务，但其背后的技术挑战随着规模增长而急剧放大：单机连接数受限、跨机消息路由、数据一致性与可用性权衡、消息堆积与持久化、AI 能力接入等。

本课程要求从工程化角度完成一个大型软件系统的物理架构、逻辑架构、运行架构、开发架构、数据架构（"五视图"）分析与设计，并在此基础上完成原型系统开发，非功能目标要求实现高并发、高可用、高可扩展。集群聊天服务器正是覆盖上述全部技术挑战的最佳载体：它既有典型的业务分层（接入、业务、数据），又天然面临分布式难题（跨服务器消息、缓存一致性、数据库读写分离），还具备向 AI 智能助手延伸的扩展空间。

## 1.3 项目目标

本项目的目标如下：

1. **功能目标**：实现一个功能完整的集群聊天系统，包括用户注册、登录、注销，一对一私聊、群组聊天，好友管理、群组管理，离线消息存储与登录推送，聊天历史记录分页查询，以及 AI 智能助手接入。
2. **架构目标**：系统支持多服务器实例水平扩展；通过负载均衡、缓存、读写分离保障高并发；通过主从复制、哨兵监控、多实例冗余保障高可用。
3. **AI 目标**：在聊天服务器上接入基于大语言模型的智能助手，支持自然语言对话、联网搜索和工具调用（代发消息、查询好友/群组/在线用户等），增强系统智能化水平。
4. **工程目标**：提供 Web 前端原型（React），提供 Docker 一键部署（17 个容器），提供完整的测试体系与文档，保证系统可以在 Linux 环境一键运行、现场可演示。

# 2. 整体功能概述

## 2.1 整体系统概述

ChatPulse 是一个基于 muduo 网络库开发的高性能集群聊天服务器，采用 Protobuf 二进制协议作为唯一序列化格式，通过 Kafka 消息队列实现多服务器之间的实时消息广播，Redis 作为缓存层加速热点数据读取，MySQL 主从架构配合自动读写分离实现数据持久化。系统集成 AI 智能助手（LangChain + LangGraph + ModelScope LLM），支持自然语言对话、联网搜索、代发消息与信息查询。系统提供 React Web 前端与 Python Bridge 网关，浏览器即可完成注册、聊天、AI 互动等全部操作，并可通过 Docker Compose 一键部署 17 个容器。

系统整体由五个层次组成：

- **用户层**：React + TypeScript 单页应用，提供登录注册、好友/群组管理、聊天窗口、AI 对话界面；
- **接入层**：Python Bridge（FastAPI），向上提供 REST + WebSocket 接口，向下通过 TCP + Protobuf 与服务器通信；
- **服务层**：3 个 ChatServer 实例（C++），Nginx TCP 四层负载均衡（轮询）；
- **AI 层**：AI Agent 服务，通过 TCP 收发消息、通过 MCP HTTP 调用服务器工具；
- **数据层**：MySQL 主从（读写分离）、Redis 主从 + Sentinel（缓存）、Kafka（跨服消息）。

## 2.2 整体用例分析

系统涉及两类参与者：

- **普通用户**：注册、登录、私聊、群聊、好友管理、群组管理、历史查询、AI 对话；
- **AI 智能助手**（系统参与者）：接收用户消息并回复，通过 MCP 调用服务器工具代为执行操作；
- **系统管理员**（预留）：以 admin 账号登录，查看在线用户与服务器统计。

## 2.4 其它（部署方案概述）

系统采用 Docker Compose 编排 17 个容器实现一键部署：基础设施层 10 个（MySQL 主 1 从 2、Redis 主 1 从 2 + Sentinel×3、ZooKeeper、Kafka），服务层 4 个（ChatServer×3、Nginx），AI 与前端层 3 个（Bridge、Agent、Web）。所有服务相互通过 Docker 内部网络通信，端口按标准映射到宿主机。详见第 6 章物理架构设计。

## 3.4 消息通信子系统

### 3.4.1 一对一私聊（UC-004）

| 使用标识 | UC-004 | 用例名称 | 一对一私聊 |
|----------|--------|----------|----------|
| 用例描述 | 用户向好友发送私聊消息；无论对方在线或离线消息均不丢 |
| 参与者 | 普通用户 | 前置条件 | 已登录、对方为好友 |
| 事件流—基流 | 1. 输入消息发送；2. Bridge 经 TCP 发送 ONE_CHAT_MSG；3. 服务端先写入 chat_message 历史表；4. 查本机连接映射：对方在本机则直接推送（EventLoop 线程安全发送）；5. 对方不在本机则经 PeerRelay/Kafka 广播到所有服务器，由对方所在服务器推送；6. 对方离线则写入 offlinemessage 表，登录时推送 |
| 分支流 | 4.1 对方在本机但状态缓存为离线（超时）：以缓存为准走离线存储 |
| 替代流 | 5.1 Kafka 不可用：PeerRelay 直连通道兜底；5.2 两者均失败：本地离线存储（仅影响跨服在线用户，Redis 去重防重复） |
| 后置条件 | 消息已持久化；接收方在线收到实时推送或离线登录后收到 |
| 非功能需求 | 发送响应 < 500ms；同一消息不会重复存储（Redis SETNX 去重键） |
| 优先级 | 高 |

### 3.4.2 群组聊天（UC-005）

| 用例描述 | 用户向群内全体成员广播消息 |
| 事件流—基流 | 1. 发送 GROUP_CHAT_MSG；2. 写入 chat_message（msg_type=2）；3. 查询群成员列表，本机在线成员直接推送；4. 其余成员：状态在线则经 Kafka/PeerRelay 跨服投递，离线则写离线表（SETNX 去重） |
| 替代流 | 4.1 发送者所在服务器不重复消费自己的广播（发送方在线校验） |
| 优先级 | 高 |

### 3.4.3 聊天历史查询（UC-009）

| 用例描述 | 按聊天类型（私聊/群聊）与 peer 分页查询历史消息 |
| 事件流—基流 | 1. 前端首次打开聊天窗口发送 GET_CHAT_HISTORY_MSG；2. 服务端按 msg_type + from/to + 时间倒序查询 chat_message；3. 以 Base64 编码的消息列表返回，前端去重合并 |
| 优先级 | 中 |

## 3.5 AI 智能助手子系统

### 3.5.1 AI 智能对话（UC-010）

| 使用标识 | UC-010 | 用例名称 | AI 智能对话 |
|----------|--------|----------|----------|
| 用例描述 | 用户与 AI 助手对话；AI 可联网搜索、调用 MCP 工具代执行操作 |
| 参与者 | 普通用户、AI 智能助手 | 前置条件 | 已登录，AI 助手在线（ID=10000） |
| 事件流—基流 | 1. 用户向 AI 助手（好友 10000）发送消息；2. ChatServer 将消息经 TCP 转发给 Agent 服务；3. Agent 加载三层记忆，调用 LLM 推理；4. 需要信息时通过 MCP HTTP 调用 ChatServer 内置工具（查好友/查用户/查在线/服务器统计）；5. 需要实时信息时调用 Tavily 联网搜索；6. 合成回复经 TCP 返回 ChatServer，再经 Bridge 的 WebSocket 推送到用户浏览器 |
| 分支流 | 3.1 对话超 40 轮：滑动窗口 + LLM 摘要压缩，控制上下文长度 |
| 替代流 | 3.2 主模型限流：自动切换备用模型（MiniMax → GLM-5 → DeepSeek-R1）；3.3 未配置 API Key：以 Dummy 模型运行（开发模式） |
| 后置条件 | 对话历史写入 Redis（7 天 TTL），Agent 重启后可从 MySQL 兜底恢复 |
| 非功能需求 | 回复延迟可接受（LLM 推理为主）；单用户对话记忆与其他用户隔离 |
| 优先级 | 高 |

## 7.3 设计规范

- **单一职责**：网络、业务、数据三层分离，ChatServer 不直接操作 SQL，Model 不触网；
- **依赖倒置**：业务层依赖抽象 Model/DatabaseRouter 接口，不依赖具体连接；
- **开闭原则**：新增消息类型只需注册 Handler，不改动网络层；
- **线程安全**：共享连接映射由互斥锁保护；跨线程发送统一经 EventLoop runInLoop 投递；
- **幂等性**：数据库写入使用 insert ignore / ON DUPLICATE KEY；跨服离线消息用 Redis SETNX 去重；
- **配置外置**：所有连接参数通过环境变量注入，不硬编码。

# 8. 功能设计

## 8.1 用户管理模块

### 8.1.1 用户登录功能

**功能描述**：校验用户凭据；维护本机连接映射 `_userConnMap`（互斥锁保护）；更新 DB 状态与 Redis 缓存；下发离线消息、好友与群组数据；处理重复登录与密码错误；自动补建 AI 好友与公共群组。

**功能类图（核心类）**

| 类名 | 关键成员 | 职责 |
|------|----------|------|
| ChatService（单例） | `_userConnMap`, `_connMutex` | 登录/登出/收发消息的业务编排 |
| UserModel | `query(id, forceMaster)`, `updateState()` | 用户 CRUD 与状态维护 |
| FriendModel | `query(userid)`, `insert(a,b)` | 好友关系 |
| GroupModel | `queryGroups(userid)`, `addGroup()` | 群组与成员 |
| OfflineMsgModel | `query/insert/remove` | 离线消息 |
| ChatHistoryModel | `insert/queryPrivateChat/queryGroupChat` | 历史持久化 |
| CacheManager | `cacheUser/cacheUserStatus/invalidate*` | 分级缓存 |

**登录时序（关键路径）**

```
用户 → Bridge → ChatServer(login):
  1. 解析 LoginRequest，查询 user 表（forceMaster）
  2. 密码校验 → 失败 err_num=1；已在线 → err_num=2
  3. 加锁写 _userConnMap[id]=conn；DB 置 online；写缓存
  4. 查离线消息 → 下发并清空 offlinemessage 表
  5. 查好友列表（确保含 AI 10000）、群组及成员 → 组装响应
  6. Bridge 解析响应 → 建立 WebSocket → 前端进入主界面
```

### 8.1.2 数据库方案设计

**1）技术方案**：MySQL 8.0 InnoDB；写操作路由主库、读操作路由从库（DatabaseRouter 自动路由，可 forceMaster 强一致读）；连接池（主 10 / 从 10×2）；字符集 utf8mb4；全部 SQL 使用转义防注入。

**2）数据库环境**：

| 序号 | 数据库名称 | 数据库及版本 | 用途 |
|------|-----------|---------------|------|
| 1 | chat（master） | MySQL 8.0 | 主库，全部写操作 |
| 2 | chat（slave1） | MySQL 8.0 | 从库 1，读操作 |
| 3 | chat（slave2） | MySQL 8.0 | 从库 2，读操作（轮询） |

**3）数据库表设计**：

**user 用户表**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | INT AUTO_INCREMENT PK | 用户 ID |
| name | VARCHAR(50) UNIQUE | 用户名 |
| password | VARCHAR(50) | 登录密码 |
| state | ENUM('online','offline') | 在线状态 |
| created_at / updated_at | TIMESTAMP | 时间戳 |
| 索引 | idx_user_state(state) | 在线用户查询 |

**friend 好友关系表**：`(userid, friendid)` 联合主键，双向外键 CASCADE，`idx_friend_userid/idx_friend_friendid`。

**allgroup 群组表**：`id PK, groupname UNIQUE, groupdesc`。

**groupuser 群组成员表**：`(groupid, userid)` 联合主键，`grouprole ENUM('creator','admin','normal')`，外键 CASCADE，双向索引。

**offlinemessage 离线消息表**：`id PK, userid, message LONGBLOB`（二进制 protobuf），`idx_offlinemessage_userid` 关键索引（登录拉取）。

**chat_message 聊天历史表**：`id PK, msg_type(1私聊/2群聊), from_id, to_id, content, msg_time`，复合索引 `idx_chat_private(msg_type,from_id,to_id,msg_time DESC)`、`idx_chat_group(msg_type,to_id,msg_time DESC)` 支持按聊天对象分页查询。

**4）系统维护设计**

- **升级维护**：Docker 镜像版本化，`docker compose up -d --build` 滚动升级；schema 变更遵循"先加列后删列"；
- **灾备与恢复**：主库数据卷每日备份（mysqldump 即可）；从库即实时灾备，主库故障时从库可提升；`docker compose down -v` 可完全重置演示环境；首次启动自动执行 init.sql 建表脚本与主从复制配置。

## 8.2 消息通信模块

### 8.2.1 私聊消息功能

**功能描述**：先持久化历史，再按"本机在线 → 跨服广播 → 离线存储"三级降级路径投递；跨服投递结果与离线存储用 Redis SETNX 去重防止同一条消息被多个服务器各存一份。

**发送时序（对方在另一台服务器）**

```
用户A(Server1) → Bridge → ChatServer1:
  1. 写 chat_message 历史表
  2. 查找本机 _userConnMap：B 不在此机
  3. PeerRelay/Kafka 发布 user_messages topic
  4. Server2 消费者收到 → 本机找到 B → 推送
  5. B 不在任何服务器在线 → 各服务器以 Redis 去重后写入离线表
  6. B 登录 → 拉取离线消息 → 经 Bridge WebSocket 推送到浏览器
```

### 8.2.2 群聊消息功能

**功能描述**：查群成员 → 本机成员直接推送 → 非本机成员按在线/离线处理 → Kafka/PeerRelay 广播给其余服务器；发送方所在服务器不重复消费自己的广播（在线校验）。

## 8.3 AI 智能助手模块

### 8.3.1 AI 对话功能

**功能描述**：Agent 以固定账号（10000）经 TCP 收发用户消息，LangGraph 状态图编排"推理 → 工具调用 → 再推理"，MCP 适配层把 ChatServer 的 9 个业务工具暴露给 LLM。

**三层记忆架构**

| 层 | 存储 | TTL/策略 | 作用 |
|----|------|----------|------|
| Layer 1 | Redis db=1 | 7 天 | 会话上下文持久化，跨会话恢复 |
| Layer 2 | LLM 摘要 | 超 40 轮触发 | 滑动窗口 + 摘要压缩，控制上下文长度 |
| Layer 3 | MySQL chat_message | 30 天清理 | Agent 重启后兜底恢复历史 |

### 8.3.2 MCP 工具清单

| 工具 | 功能 |
|------|------|
| chat_user_login | 验证用户凭据 |
| chat_send_message | 代发私聊消息 |
| chat_server_stats | 服务器统计 |

# 9. 非功能设计

## 9.1 高并发设计

**需求描述**：支撑大量在线用户同时收发消息；保证热点数据读取性能。

**设计方案**：

1. **分层负载均衡**：Nginx TCP 四层负载均衡（轮询算法）把连接均匀分发到 3 个 ChatServer，每实例独立服务，容量随实例数线性扩展；
2. **多级缓存**：Redis 按数据热度分级 TTL——用户信息 30 分钟、好友列表 15 分钟、群组信息 10 分钟、在线状态 5 分钟；登录等高频读直接命中缓存；
3. **读写分离**：DatabaseRouter 把读请求路由到从库，写请求留在主库，将主库写压力与读压力隔离；连接池动态扩容（主 10 / 从 20）；
4. **异步化**：跨服消息经 Kafka 异步解耦，发送请求无需等待对端服务器处理；
5. **异步日志**：muduo 风格双缓冲日志，写日志不阻塞业务线程；
6. **事件驱动网络**：muduo Reactor 模型 + 4 IO 线程，单连接资源占用小，支持千级并发连接。

## 9.2 高可用设计

**需求描述**：任一组件故障不影响整体服务；数据不因单点故障而永久丢失。

**设计方案**：

1. **MySQL 高可用**：主从异步复制（从库首次启动自动配置复制），读流量从从库出；主库故障时连接池自动标记不可用并降级到从库；
2. **Redis 高可用**：一主两从 + 3 个 Sentinel 哨兵（quorum=2），主节点故障自动选举提升从节点为新的主节点；
3. **服务高可用**：3 个 ChatServer 实例互不依赖（无共享架构），任一实例宕机，Nginx `max_fails=3 fail_timeout=30s` 自动剔除，其余实例继续服务；
4. **AI 容错**：模型限流时自动轮换备用模型（MiniMax → GLM-5 → DeepSeek-R1）；无 Key 时降级 Dummy 模型；
5. **消息不丢**：离线消息落 MySQL 持久化；跨服消息 Kafka 持久化（可重放）；
6. **进程自愈**：全部容器 `restart: unless-stopped`；Bridge 提供 `/api/health` 健康检查；ChatServer 启动时自动重置残留在线状态。

## 9.3 高可扩展设计

**需求描述**：容量不足时以最低成本扩展；新增功能不影响既有架构。

**设计方案**：

1. **水平扩展**：新增 ChatServer 实例 = 新增一个容器 + 一个端口，业务代码零修改——实例端口即 Kafka 消费组 ID 后缀，广播语义自动成立；
2. **Kafka 解耦**：服务器间只依赖消息队列契约，任意数量实例均可加入/退出；
3. **插件式 MCP**：AI 能力以工具注册表形式扩展，新增工具 = 注册一个 Handler，不影响既有协议；
4. **服务化分层**：Bridge/Agent/Web 可独立部署、独立扩容；基础设施通过 Docker 网络解耦；
5. **Docker 编排**：compose 文件参数化（实例数、端口、凭据均可配置），部署拓扑可一键调整。

## 9.4 一致性设计

**需求描述**：分布式环境下消息不重不漏；缓存与库最终一致。

**设计方案**：

- 消息去重：跨服离线消息 + 原始服务器同时写离线表时，用 Redis `SETNX` 去重键（30 秒 TTL，键含 from/to/时间戳）保证只落一份；
- 缓存失效：写操作即时失效对应缓存（好友变更失效双方好友缓存、状态变更失效状态缓存）；
- 读一致性：登录、历史等强一致场景 `forceMaster=true` 强制走主库；
- 状态补偿：服务器启动将全部用户重置为 offline（防僵尸在线状态）；
- 幂等写入：`insert ignore`、`ON DUPLICATE KEY UPDATE` 保证重复消息不产生重复行。

# 10. 软件原型系统设计

## 10.1 原型概述

本系统的原型采用 React + TypeScript 技术栈实现为**可运行的真实 Web 应用**（非静态图纸），与"软件原型系统"要求的可用性、可演示性目标一致。原型通过浏览器完成全部业务演示：

- **登录/注册页**：账号密码输入、注册即得 ID、错误提示；
- **主界面（侧边栏 + 聊天区）**：
  - 好友区：好友列表（在线绿点/离线灰点）、筛选、快速加好友、AI 智能助手置顶；
  - 群组区：群列表、创建群组、加入群组；
  - 聊天区：Markdown 渲染消息气泡、时间显示、流式推送、聊天历史自动加载；
  - AI 对话：支持 Markdown 渲染的 AI 回复（推理过程剥离）、思考标签隐藏。
